### 2.2 Daily bar timestamps: the bar is stamped at **London midnight**

| Period | Stamp observed | London time | UTC date vs London date |
|---|---|---|---|
| GMT (winter, e.g. 2026-11-16) | `2026-11-16T00:00:00Z` | `00:00` | same day |
| BST (summer, e.g. 2026-03-29) | `2026-03-29T23:00:00Z` | `2026-03-30 00:00` | **previous day** |

Consecutive daily bars around the spring DST switch (`--weekends`, USD):

```
2026-03-26 Thu=6.90100 | 2026-03-27 Fri=6.91070 | 2026-03-29 Sun 23:00=6.91160 | 2026-03-30 Mon=6.91160 | 2026-03-31 Tue=6.89420
```

One-year stamp histogram (all ten pairs identical):

```
bars=262 first=2025-11-17 last=2026-11-17 weekends=30
Mon=53, Tue=53, Wed=52, Thu=52, Fri=22, Sat=0, Sun=30
gaps>4d: none
```

That is exactly a one-day UTC shift for the ~30 BST weeks (the "Sunday 23:00"
bars are London Mondays): a bar's identity is its **London calendar date**,
not its UTC date.

### 2.3 Session structure (hourly)

57 hourly bars over three days; spacing min 0.67 h, max **49 h** — the gap
`Fri 23:00Z → Mon 00:00Z`. The FX week in this feed is Mon 00:00 → Fri 23:59
UTC; there are no Saturday bars and no Sunday bars in the hourly series (the
Sunday stamps in §2.2 are the BST convention, not Sunday trading).

### 2.4 The current-day bar is live, not closed

At `2026-11-17T07:39Z` the 2026-11-17 bar close was `6.664900`, identical to
`meta.regularMarketPrice` `6.6649`. The bar keeps moving until the London day
ends, so treating its stamp as a *close* (or its UTC date as the rate date)
both mislabels the data.

## 3. Findings

| ID | Severity | Finding | Evidence |
|---|---|---|---|
| F-FX-01 | **P1** | FX dates are one day early in BST: `_frame_from_chart` normalises the stamp to UTC midnight, so a `23:00Z` summer bar is labelled the previous day. Every summer FX return therefore uses the previous day's move. | §2.2 histogram + timeline |
| F-FX-02 | **P1** | FX is never persisted: `save_fx`/`load_fx` have no production callers (grep), `fx_rates` has 0 rows, and each estimate re-downloads ~11 days per currency with no cache or reuse. | `repository.py:472,528`; live DB probe |
| F-FX-03 | **P1** | FX rows are structurally non-PIT: `fx_series_map` leaves `available_at=None`, `availability_source=unknown`, and no code path fills them, so no FX observation can ever be used for look-ahead-safe history. | `fa/data/fx.py:112` |
| F-FX-04 | P2 | No quote-direction assertion: `FX_TICKERS` mixes the irregular `CNY=X` with `<CUR>CNY=X`, and nothing checks a returned magnitude. A vendor symbol redefinition would silently invert the FX leg (numbers still look plausible). | §2.1; `fa/data/fx.py:22-33` |
| F-FX-05 | P2 | `fa/data/fx.py::rate_on()` is dead code and measures staleness in **calendar days** (`max_stale_days=7`), while the live path measures **sessions**. Two incompatible definitions waiting to be mixed up. | grep: no callers |
| F-FX-06 | P2 | Batch download is sequential (one request per currency) and has no cache: a 10-currency portfolio costs 10 round trips per estimate, and a failed currency silently drops the FX leg. | `fa/data/fx.py:66-76`; `nav_estimator.py:197` |
| F-FX-07 | P3 | `_frame_from_chart` does not deduplicate repeated dates; `save_fx` would collapse them via `ON CONFLICT` without a word. | `qdii_market.py:96-118` |
| F-FX-08 | P3 (note) | `align_fx()` resolves `calendar_for(None, None)` → `FallbackCalendar` (Mon–Fri, no holidays). For FX this is *correct* (FX trades on UK bank holidays) but it is accidental, and any future "FX calendar" must keep this property. | `price_alignment.py:221` |
| F-FX-09 | P2 | Time-zone data is not declared. `zoneinfo` works in both verified interpreters (`tzdata` 2025.2 / 2026.4 installed) but `requirements.txt` does not list it, and `fa/utils/calendar.py:33` deliberately avoided `ZoneInfo` because "Windows 上沒有系統 tzdata". A London-date rule cannot be done with a fixed offset (BST). | §2.2; `requirements.txt` |

### 3.1 Consequences that are *not* defects

- No weekend or holiday gaps in FX data (`gaps>4d: none`) — FX needs no holiday
  table, only Mon–Fri.
- `Price = AdjClose.fillna(Close)` is harmless for currencies (Yahoo returns no
  `adjclose`), but the pipeline must not describe FX as an adjusted price.
- 262 bars/year with no 4-day gap means the 5-session overlap window translates
  to at most 9–10 calendar days (weekends only).

## 4. Decisions settled by this audit

| ID | Decision | Evidence |
|---|---|---|
| D-1 | An FX bar belongs to a **Europe/London** date `D`; the vendor stamp is `D 00:00 London` (bar start). `available_at = (D+1) 00:00 London + 30 min`, `availability_source = inferred`, note states both facts. A live bar therefore has a future `available_at` and is excluded by PIT without a special rule. | §2.2, §2.4 |
| D-2 | FX revisions get their own `fx_revisions` table via Migration 003 (purely additive; no back-fill needed because `fx_rates` is empty). `price_revisions` keys on ticker/price_type and cannot host FX without a fake ticker. | `schema.py:17,73,237`; DB probe |

Full rationales, rejected alternatives and the module contracts are in
[09_v231_stage2_fx_pipeline](../technical_specification/V2/09_v231_stage2_fx_pipeline.md) §2.

## 5. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Fixing F-FX-01 changes one FX observation per summer estimate (numbers move slightly) | Stage 2.5 smoke runs the 000369 estimate before/after and records both; the change is documented in the release notes |
| Writing today's live bar creates a revision row when the day closes | Accepted by design: PIT already ignores a future `available_at`, and the ledger is exactly for this settlement (§3.3 of the spec) |
| `tzdata` missing on a future machine (F-FX-09) | `london_offset()` uses `ZoneInfo` when importable and falls back to the documented EU DST rule (last Sunday of March 01:00 UTC → last Sunday of October 01:00 UTC); a test asserts both agree for every day 2025–2030. `requirements.txt` stays unchanged |
| Migration 003 corrupting a live database | Same atomic runner as Migration 002, proven against the frozen baseline copy, with a byte-identical check on the baseline file itself |
