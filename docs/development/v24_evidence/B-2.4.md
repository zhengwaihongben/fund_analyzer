Testing that `close()` was *called* is not treated as proof that the handle is
closed. Only the four closure tests (B2.4-04, B2.4-05, B2.4-06, B2.4-07) go
further: each captures the `Repository` instance passed to `close()` and then
executes `SELECT 1` on its `_conn`, asserting `sqlite3.ProgrammingError`. The
JSON-read-only tests (B2.4-01/02/03) do not execute SQL on the captured
connection — they assert file bytes/mtimes and write-method call counts.

## 4. Findings

No defect was found in `fa/application/estimation.py`; the file was not
modified in this batch. The JSON-reading path can raise only through a
programming error (`_read_json` already swallows `OSError`/`ValueError`), and
that case is what B2.4-07 pins: the exception still propagates and the
repository still closes, because both entry points use `try/finally`.

## 5. B2.4-08 — SQLite initialisation side effects (added after review)

`Repository(db_path)` calls `fa.data.database.connection.connect()`, which
unconditionally runs `PRAGMA journal_mode = WAL` and `initialise(conn)`.
`initialise()` reads the schema version, applies pending migrations, and for
`version >= 4` always runs `BEGIN IMMEDIATE` + `_apply_columns(REVIEW_COLUMN_REPAIRS)`
+ `COMMIT` — even when the column already exists and nothing is altered.

Four tests were added to pin what that means for stored mode:

| Test | Result |
| --- | --- |
| `test_b2_4_08_initialise_runs_when_the_repository_opens` | `initialise()` is called exactly once per `load_estimate()` and per `list_estimates()` — the read path does go through migration code |
| `test_b2_4_08_initialise_leaves_schema_rows_and_versions_unchanged` | on an up-to-date DB, `sqlite_master`, `schema_version` rows, per-table row counts and the estimation rows/inputs/results are byte-for-byte identical before and after; WAL/main file sizes are recorded but deliberately not asserted (checkpointing can move bytes without a logical change) |
| `test_b2_4_08_no_migration_is_applied_and_no_table_is_created` | `MAX(version)` and the table set are unchanged |
| `test_b2_4_08_a_read_opens_a_writable_connection_without_writing` | captures the connection inside the `initialise()` hook and asserts `PRAGMA query_only = 0` (SQLite itself would accept a write), then re-checks the logical fingerprint; documents the boundary honestly: stored mode is not a read-only handle |

**Finding (not a stored-mode write, but a real boundary):** on an up-to-date
database these tests show no logical change at all. However, the read path
still opens a write-capable connection and executes `BEGIN IMMEDIATE`, and on
a database with pending migrations the same call would migrate it. That is
`connect()`'s documented contract ("open and migrate"), not a write performed
by `load_estimate()`. A strictly read-only handle would require a Repository /
connection change (for example opening `mode=ro` or adding a `migrate=False`
option); that is outside this batch's allowed edits, so it is recorded here as
a known limitation rather than silently changed.
