# A-06 — worker data boundary and widget isolation

Stage A evidence for acceptance item **A-06**: "a worker holds no widget
reference: the service input is plain data, and a source review finds no
closure/callback/global widget escape".

Revised after the Stage A independent review found that the §13.1 original
claim ("worker does not touch a widget") is weaker than T-9 ("worker holds no
Tk widget reference").  This revision is based on the actual reference
structure of the running threads, not on the absence of widget calls.

## 1. Reference rule

A worker thread may hold plain Python data, queues, events, module-level
functions and `ProgressReporter` instances.  It may **not** reach a Tk widget
through any path:

| Path | Rule |
| --- | --- |
| Thread target | module-level function (`fa.gui.worker._execute_worker`), never a bound method |
| Work callable | module-level function or closure-free callable; never a bound method of a window |
| Progress channel | `ProgressReporter`, holding exactly `(queue, closed_event)` via `__slots__` |
| Arguments | plain data only (`str`, `Path`, `dict`, `bool`, `Queue`) |
| Callbacks (`on_progress`, `on_result`) | kept by `WorkerBridge` on the main thread; never passed to the worker |

## 2. Reference structure, per thread path

`fa/gui/worker.py`

```text
threading.Thread(target=_execute_worker,
                 args=(work, args, kwargs, queue, closed_event, reporter))
```

`_execute_worker` is module level (`__self__ is None`, `__closure__ is None`),
so the thread does not hold the `WorkerBridge`, and the bridge's `_widget`
reference stays on the main thread.  `ProgressReporter` has
`__slots__ = ("_queue", "_closed_event")` and no `__dict__`, so it cannot carry
a widget even by accident.  `WorkerBridge.submit()` documents this contract.

`fa/gui/qdii_estimate.py`

```text
threading.Thread(target=_run_qdii_estimate,
                 args=(fund_code, save_dir, result_queue), name="qdii-estimate-worker")
```

The previous `target=self._task` (bound method holding the whole
`QdiiEstimateWindow`) was removed; `_task` no longer exists.

`fa/gui/post_market.py`

```text
threading.Thread(target=_fetch_post_market_task,
                 args=(fund_code, save_dir, result_queue), name="post-market-worker")
```

The previous local `task()` closure captured `self.fund_code`,
`self.save_dir` and `self.result_queue` and therefore the window; the closure
is gone and the module-level function receives the three plain values.

## 4. Close timeout (T-7)

- `WorkerBridge.close()` clamps every caller-supplied wait to
  `MAX_CLOSE_SECONDS = 2.0` through `_bounded_timeout()`; negative values clamp
  to 0, NaN to 2.0.
- `WindowRegistry.close_all(timeout=...)` treats `timeout` as the **shared**
  budget for all children: it computes a deadline with `time.monotonic()` and
  passes each child only the remaining time.  Two children therefore cannot
  each wait two seconds.  The budget bounds worker joins only; Tk `destroy()`
  and user close callbacks are not forcibly terminated and the code does not
  claim otherwise.
- The QDII and post-market windows accept `close(timeout=...)` and clamp it the
  same way.

Tested by `test_close_timeout_is_capped_at_two_seconds` (elapsed < 2.5 s with
`close(timeout=30.0)`) and the two registry budget tests.

## 5. Known limits

- A Python thread cannot be force-killed.  Close waits at most two seconds and
  then stops listening; the work may still run until its current call returns.
  Nothing it sends after close reaches a widget (the closed event short-circuits
  `ProgressReporter.report` and the terminal put).
- The `session_price`-style "conservative superset" concern does not apply
  here; the isolation rule is structural and checked on the live threads.
- The `submit()` guard blocks **common direct references** only: a bound method
  (`__self__`) and a closure that captures a Tk widget, a `WorkerBridge`, or a
  handle exposing `after`/`after_cancel`.  It does not inspect `args`/`kwargs`,
  nor a closure that captures an ordinary controller which itself holds a
  widget; those remain covered by the live-thread tests for the three shipped
  paths, not by the guard.  Hardening `args`/`kwargs` is recorded as a follow-up
  item, not as a claim of complete GUI-reference detection.
